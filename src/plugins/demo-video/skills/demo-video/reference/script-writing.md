# Writing demo scripts that record well on the first try

A demo script (`e2e/demos/<slug>.demo.ts`) is a screenplay, not a test. Each take = one visual beat the viewer watches while one narration sentence plays. Narration length sets the clip's minimum length (video freeze-pads to fit), so **footage longer than its narration is dead air**.

```typescript
import { expect } from '@playwright/test';
import { defineDemo } from '../demo/define';

export default defineDemo({
  feature: 'Human-readable feature name', // title card + slate narration text
  slug: 'kebab-case-slug',
  takes: [
    {
      narration: 'One sentence describing this interaction.',
      action: async (page) => {
        await page.goto('/dashboard');
        await expect(page.locator('.panel')).toBeVisible();
        await page.waitForTimeout(800); // orient dwell (first take)
      }
    }
  ]
});
```

## Take scoping — the one rule that matters

One take = ONE thing the viewer watches: a page appearing, a modal being filled, a row expanding. If an action list reads "navigate AND open AND fill AND save", split it — each half gets its own narration sentence.

Budget: a narration sentence plays ~4-6s. Keep a take's interactions to roughly that (a glide + a click + a short dwell). A form fill is its own take; the save+result is another.

## Narration style

- Write narration FIRST; actions illustrate it. Spoken register, present tense, ≤ ~15 words. Read it aloud.
- Describe what the viewer SEES, not the implementation ("The audit log lists every change" — not "rows are inserted into the audit_log table").
- The subtitle pill wraps at ~42 chars/line to two lines max; longer lines shrink readability.
- Real `expect()` calls in every action so the recording fails loudly if the feature breaks.
- No login in takes — the runner logs in before recording starts.

## Selector rules

- Prefer semantic selectors: roles (`getByRole`), stable classes. Never framework binding attributes.
- Read the actual templates/components for every page you touch before writing selectors — titles, classes, icons. Do not write selectors from memory.
- Custom-element hosts often have no box — `toBeVisible()` on them lies. Assert on an inner element that actually renders.
- Angular `[(ngModel)]` inputs need `pressSequentially` (`fill()` doesn't trigger ngModel); `formControlName` inputs accept `fill()`. Angular `<select>` with `[ngValue]` needs `selectOption({ label: '...' })` — DOM values are compound.
- Filter table rows by text the row ACTUALLY renders (read the template's columns), not values you hope are there.
- Scope reused styling classes with `:has(<something unique to the row>)`.

## Motion + dwell architecture

- Use `glideTo` / `glideClick` / `smoothScrollBy` from `e2e/demo/actions.ts` for everything the viewer should follow. Raw `.click()` teleports.
- First take: after the page settles, dwell ~800ms BEFORE acting so the viewer orients.
- Middle takes: end with 600-900ms dwell.
- LAST take: end with `waitForTimeout(4500)` — the closing dwell must outlast its narration so the final subtitle clears and the page holds clean before the fade/outro.

## Merged videos (several features, one video)

`video:merge -- <slug>... --out <out-slug>` concatenates recorded demos.

- **Never write the brand line into a take's narration.** It belongs to the opening slate ONLY, generated by the pipeline (`openingNarration`). `assertSingleIntro` blocks a merge that would repeat it.
- Slate narration is generated from a fixed table ("Next up: / Then: / Also:"); edit `scripts/demo/narration.ts` to change wording, never special-case at render time.
- `feature` is the slate text AND the transition line — it must read as a spoken phrase after "Next up:".
- Each demo must stand alone but not re-orient ("Let's start by logging in" is wrong — in a merge it may be minute three).
- Last-take 4500ms dwell applies per segment.
- Play order lives in the merge command (and wherever the project records provenance) — the merge never sorts.
- Sources must be recorded first (`video:build` each, or pass `--record`).

## Verify like a viewer

After `video:build -- <slug>`: extract frames at cue boundaries (`ffmpeg -ss <t> -i <out>.mp4 -vframes 1 f.png`) and LOOK at them, then watch the whole mp4. A green build proves assertions passed, not that the video reads well.

For a merge, read the printed narration plan before rendering, and LISTEN to each slate boundary: the brand line audible once at the top and never again; the outro only at the very end.

## Common mistakes

- Cramming a whole CRUD flow into one take → one subtitle then 15s of silent footage. Split it.
- Writing narration after the actions.
- Selectors from memory instead of from the actual templates.
- Recording against a dirty database — stale rows appear on video.
- Merging demos that were never recorded → merge fails naming the missing slug.
